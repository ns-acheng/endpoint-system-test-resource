What the review of our first plan found

Execution steps per case (median):

Whole Windows suite (125 rows): 6
EPAIS plan (9 rows): 3

Cause: the first plan was built only from idle-client facts, so every case was an observation, not a scenario (baseline → act → verify → restore → back to baseline).

What we did about it

  • Step table per case added (5–10 steps, each step names its helper).
  • Coverage matrix of the MVP test plan against our cases; 22 E2E rows were not referenced at all.
  • 15 new cases drafted (EPAIS-31..45): 2 are keep (36 logs with the daemon stopped, 38 selectors), the rest are needs-POC because their pass fact is not observed yet.
  • Evidence rule applied per assertion, not per case.

Part 2 — how GRS tests the client

Flow 6 · From a trigger to a stored result

1

Trigger

Jenkins lane (REG, REG2 for reboot-class cases; LOCAL lanes; MAC2-SSH for the mac guest). Params: branch, case, tenant, dc, release or build_url.

2

Target VM

Lane resolves the VM; SSH preflight fails fast on a dead VM.

3

Install client

test_01_install_client via check_client_installation: install, enroll by invite, verify with nsdiag.

4

Case body

Baseline, act, verify, restore, baseline again; probes read logs, files, services, the tenant API.

5

Gates

Health gates (memory, handles, crash dumps, reboot count) run around every case.

6

Artifacts

Client logs and config are zipped and archived with the build.

7

Results DB + report

Ingested into PostgreSQL; the HTML report (this page's style) shows runs per release.

Good points of GRS — why a new feature is quick to pick up

1 · One case, one run

A failure points at one case. Lanes queue; there is no wall of "deselected" noise.

2 · Tenant and dc by tool

dc-pick reads a map of validated combinations and refuses unapproved tenants. No hand-written params.

3 · Install is part of the case

Every case begins from a verified client, so a result always carries the client version.

4 · Feature builds are a parameter

A feature build installs by URL on Windows and mac without touching the code.

5 · Iterations

Repeat the whole scenario N times to prove stability; the recorder stores each iteration.

6 · Safe restore

Config guard journals changes and restores them; the install-state check catches orphaned installs.

7 · Privileged helpers

A SYSTEM task runner reads (and now writes under a path guard) folders the SSH account cannot reach.

8 · Results of record

DB plus HTML report, comparable across releases and platforms.

9 · Mechanical rules

Gate and hooks enforce the habits (scope, DCO, no force push, evidence first), so new agents do not need to remember them.
