2. What counts as automated

The Status column of the workbook is not reliable (see data quality), so the code is the authority. A plan case is automated when GRS origin/main has a test for it: a @pyrobin.case("<id>") decorator (the plan id, or SYS-<id>) or a test_<id>_* function, on the matching platform (_win / _mac suffix or path). 98 cases are verified in code. 8 more are counted as automated only because the workbook says so and no code could be matched (VDI and two others, listed on the data-quality page). Cases marked in-progress are counted as not done.

Each of the 116 not-yet-automated cases was read in full by an agent that checked in the GRS repository whether the primitives its steps need really exist (helpers, platform clients, tenant APIs), then gave a score, an engineer-day estimate, the blocker and the missing piece. Two rules from the project owner are built in: anything that needs an outside environment scores 1, and so does anything that needs several VMs, a power or sleep state (standby, hibernate, sleep/wake; a plain reboot does not count), or a third-party product. Scores are written to the new column Automation Score (1-5) in the workbook copy task_docs/automation_forecast_2026_11/system_test_all_scored.xlsx (columns appended to the Windows and Mac sheets; the original workbook is unchanged).

4. De-duplication and merging

  1. Only cases that are not automated and scored 2-5 are merged. Automated cases are never merged into.
  2. Windows and Mac are merged separately; a Mac case and its Windows twin are different code, so they are never combined.
  3. Cases merge only when they share feature area, preconditions and setup so one test run can cover them, and their scores differ by at most 1.
  4. A merged case has at most 10 steps (checked by the build script) and still asserts every member's pass criterion.

Result: 87 plan cases became 74 merged cases. Estimated effort falls from 290 engineer-days (one by one) to 270 engineer-days (merged), because the setup is shared. A merged case takes the lowest score of its members.

5. How the forecast is calculated

  1. Unit. Engineer-days. The 98 already-automated cases were re-estimated in hindsight with the same scoring rubric (an agent read the implemented code), so history and backlog are measured in the same unit.
  2. Capacity per month = engineer-days of cases that first landed on origin/main in that month. Using the last three months (Sep, Oct, Nov; November is only 17 days old and is scaled by 30/17): Low = lowest of the three, Base = average, High = highest. Values: Low 35.0, Base 79.7, High 165.0 engineer-days per month.
  3. Order of work. Easiest first: merged cases sorted by score (5 to 2), then by estimated days. Only score 2-5 merged cases are in the plan; score 1 is excluded from the denominator of "can be automated".
  4. Month assignment. Walk down the list adding estimated days; a case completes in month ceil(cumulative days / capacity). December is month 1.
  5. Coverage = (automated now + plan cases covered by finished merged cases) / total plan cases.
  6. Time to finish everything automatable = total merged estimate (270 days) / capacity.
Interpretation of the instruction "estimate 1-4 merged cases". Score 1 means not automatable, so the estimate covers merged cases scored 2 to 5; score-1 cases are reported separately and are not in the denominator. If a different reading was meant, only step 3 changes.

Known limits of the forecast

  • History is short and uneven: only 63 merged pull requests touched system tests since July, and one week in November (week 46) delivered 40 plan cases, mostly the EPAIS batch. Low / Base / High show that spread; the Base is not a guarantee.
  • Estimates are agent judgement against the codebase, not measured effort. The hindsight estimate of the 98 finished cases uses the same method, so a bias is shared by capacity and backlog and mostly cancels in the month count, but not in the absolute day counts.
  • Product changes, new plan cases added to the workbook, lane or VM availability and tenant problems are not modelled.
