Resource monitoring guide

What every column and every chart in "Resource peaks per process", "Resource peaks per process across versions" and "Memory per process across versions" means, why it is monitored, which numbers fail a test, and which ones must not be read as a conclusion on their own. All charts are drawn from real numbers in the report database unless marked "illustration".

0. Start here (30 seconds)

Only three numbers fail a test: worst_sustained_s (CPU high for too long), worst_mem_growth (memory keeps growing), worst_handles (handles keep growing). The other columns (average peak, highest peak, average growth) are for reference and never fail a run.
Charts across versions pool all tests of a version. Each version runs a different set of tests, so a rising line does not mean the product got worse (real example in section 4).

Exception: demAgentSvc.exe (the Windows DEM agent) and epais.exe (the EPAIS AI-security service) are observe-only for now: their numbers are recorded and shown but never fail a run. A run fails only when epais.exe is not running while the client config turns EPAIS on. A process alive for less than 50% of the samples is not gated either (it was killed and restarted on purpose). Builds that carry the Shuttle/Keystone monitor change add a second group: shuttle-launcher.exe, shuttle.exe and keystone.exe (Mac: keystone) are judged like the client processes, with a first memory ceiling of 1024 MB each (a starting value, not a measurement; it is replaced by the observed 95th percentile once real runs exist); shuttle-ctl.exe (a CLI that runs for seconds), sovin.exe (the old Shuttle name an upgrade can leave behind) and on Mac keystone-auth and shuttle-launcher (it hands over to shuttle and does not stay resident) are observe-only. A process that never appears in a run shows as not alive and is skipped, not failed.

1. Where the data comes from

  • The sampler reads every monitored process every 10 seconds during a test (a few tests use 5 s). On Windows it watches stAgentSvc.exe, stAgentSvcMon.exe, stAgentUI.exe and also records demAgentSvc.exe and epais.exe (builds with the Shuttle/Keystone monitor change also shuttle-launcher.exe, shuttle.exe, keystone.exe, shuttle-ctl.exe and sovin.exe), with the thread count of each process; on Mac nsAuxiliarySvc, Netskope Client, NetskopeClientMacAppProxy and others (with the monitor change also keystone, keystone-auth and shuttle-launcher). Every process the sampler records appears in the per-process table and the cross-version charts as soon as a run holds rows for it.
  • Each test run condenses its samples into one summary row: highest CPU, sustained seconds, memory baseline and growth, highest handles. The report tables aggregate those rows per process.
  • CPU unit = per core: 100 is one core fully busy, 190 is about 1.9 cores, independent of how many cores the VM has.
  • Memory unit = MB: Private Bytes on Windows, RSS on Mac. The two must not be compared.
Figure 1: every CPU number needs the previous sample to be computed, so the first sample has no CPU value, and a reboot or process restart resets the calculation.

2. "Resource peaks per process", column by column

avg_cpu_peak - average of the highest CPU

  • Meaning: take the highest CPU of the process in each run, then average over all runs.
  • Why look: a rough baseline of "how busy is it in general".
  • How to read: it is an average of maxima, so it moves when the share of stress tests versus idle tests moves. Compare it only across the same set of tests.

worst_cpu_peak - the highest CPU reading

  • Meaning: the largest 10 s average over all runs and all samples.
  • How to read: one single point: "it has been this high once", not "it stayed there". Never fails a run. Useful to see how far it is from the threshold, for example 254.8 against 280.

worst_sustained_s - longest time above the threshold

  • Meaning: within one run, the longest stretch with CPU continuously above the threshold (figure 2 in section 3).
  • Why look: catches runaway loops and busy spins. Short spikes are normal on reconnects and config loads; only a sustained load is a problem.
  • How to read: 0 = no sample reached the threshold; 10 = exactly one sample did; the run fails at 60 s. It is almost always 0 because every process peaks far below 280 (the highest on record is 261.2).

cpu_gate - the threshold

  • Meaning: the CPU value (per core) used to decide "sustained". It is 280 for every test (2.8 cores), and the run fails after 60 s in a row. The yellow dashed line in the chart is this gate.
  • Careful: a peak above the yellow line is not a failure by itself: the run fails only after 60 s in a row above it; demAgentSvc.exe is observe-only, it is measured but never fails a run. Older runs used 140 or 240 per test; the report restates worst_sustained_s against 280: a run whose highest reading is under 280 has 0 s above the gate.

avg_mem_growth / worst_mem_growth - memory growth

  • Meaning: growth = "recent average" minus "baseline" (figure 3 in section 3). Negative = it shrank.
  • Why look: the signal of a memory leak. worst above 100 MB fails the run.
  • How to read: avg mixes positive and negative values and hides leaks, so it is of low value; worst is the useful one. Growth also depends on how long the run is.

worst_handles - highest handle count

  • Meaning: the highest handle count at any sample.
  • Why look: a handle leak eventually exhausts the process.
  • How to read: it fails only if it reached 1500 and the last sample is still at or above 1500 (figure 4). stAgentSvc.exe is at 1400 today, 100 below the ceiling: worth watching.

3. Three diagrams

Figure 2: how can we know "sustained"? Each bar is one 10 s window and the yellow dashed line is the 280 gate. The left chart is a real run: the highest bar is only 143.28, no bar reaches the gate, so worst_sustained_s = 0. If exactly one bar were above the gate the value would be 10 s: seconds = (last bar time - first bar time) + 10, so one bar is 0 + 10; six in a row = 50 + 10 = 60 s, the fail line (right chart, illustration). Note that it measures a 10 s average: a spike shorter than 10 s is flattened.
Figure 3: how memory growth is computed (real run). Baseline = median of the first 3 living samples, recent = average of the last third, growth = recent - baseline. Each boot is its own segment (memory resets on reboot, so growth across boots is meaningless); the largest segment growth is reported.
What about a client that was just installed? There is no warm-up exemption: the baseline is always the first 3 living samples of the test. Most tests start with the client already running, so the baseline is a settled value (for example STRESS-01, STRESS-08 and STEER-06 have baselines of 25-29 MB and grow only 5-8 MB); warm-up growth is far below the 100 MB threshold and does not cause false failures. Waiting until the process is ready before taking the baseline needs thread-count data first; that work is on the to-do list.
Figure 4: handles rule. A burst right after start that falls back is not a leak (real STEER-07 case: 3304 → 790 → about 920); only a count that climbs past the ceiling and stays there fails.

4. "Resource peaks per process across versions" (CPU across versions)

The per-version average (avg) trend line was removed because it moves with the test mix and cannot be read as a regression signal. What remains is the per-version "worst" chart; below is how to read it and why avg was dropped.

What is drawn now

  • X axis = client major version (from R140, one more point per release), one line per process; split into heavy (peak ≥ 30%) and light (< 30%) so light processes are not flattened. Mac has its own chart, from R143.
  • Each point is the single highest CPU reading of that version (worst). It is one 10 s average, no proof of a sustained load, and never fails a run. Read it as "has been this high", not as a trend.

Why avg (the per-version average) was removed

  • The test mix differs per version: R140 ran 15 test kinds, R142 36, R143 57, R144 only 21. A higher share of stress tests lifts the average by itself.
  • Each point is the highest of a 10 s average: the longer and more often a test runs, the more likely one high point appears.
  • One run is very unstable: the same test on the same version, STRESS-26 peaks between 49 and 162 over 16 runs.
Figure 5 (real data): left is how the old trend chart averaged, right compares only the tests both versions ran. For 143→144 the left rises 3.7, the same 14 tests rise 17: an average can exaggerate and it can hide.
Note: on R142 the same tests really did go up (17 of 24 by more than 20%) and came back down on R143. The data does not show why (product, VM or sampling conditions); that needs its own investigation, not a ticket opened from a trend line.

6. A number went up: open a ticket?

Ask three questions; open a ticket only if all three answers are "yes":
1. Is the test mix the same? Read the Tests column, or compare the same test across versions.
2. Did the same test go up too? And in more than one run.
3. Did a gate trigger? sustained, memory growth or handles.
