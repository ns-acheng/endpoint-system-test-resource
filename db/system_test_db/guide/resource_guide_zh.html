資源監控解說

這一頁解釋報表裡「Resource peaks per process」「Resource peaks per process across versions」「Memory per process across versions」每個欄位與每張圖的意思、為什麼要看、哪些會讓測試失敗、哪些不能單獨下結論。所有圖都用報表資料庫的真實數字畫成(標明「示意」的除外)。

30 秒版資料怎麼來逐欄解說三張圖解 跨版本 CPU跨版本記憶體要不要開 ticket名詞

0. 先看這裡(30 秒版)

只有三個數字會讓測試失敗: worst_sustained_s(CPU 持續太久)、worst_mem_growth(記憶體一路漲)、worst_handles(handle 一路漲)。 其他欄位(平均峰值、最高峰值、平均成長)都是「參考」,不會判定失敗。
跨版本的圖是把各版本所有測試放在一起算,每個版本跑的測試不一樣,所以線往上走不代表產品變差(第 4 節有真實例子)。

1. 資料怎麼來

  • 取樣器在測試期間每 10 秒讀一次每個被監控的 process(少數測試改成 5 秒)。Windows 監控 stAgentSvc.exe、stAgentSvcMon.exe、stAgentUI.exe,另外記錄 demAgentSvc.exe 和 epais.exe(帶有 Shuttle/Keystone 監控改動的 build 還有 shuttle-launcher.exe、shuttle.exe、keystone.exe、shuttle-ctl.exe、sovin.exe),並記下每個 process 的 thread 數;Mac 監控 nsAuxiliarySvc、Netskope Client、NetskopeClientMacAppProxy 等(有監控改動時還有 keystone、keystone-auth、shuttle-launcher)。取樣器記錄到的每個 process,只要 run 裡有資料,就會自動出現在每個 process 的表和跨版本圖上。
  • 每次測試(一個 test case 的一次 run)把這些樣本濃縮成一列摘要:最高 CPU、持續秒數、記憶體基準與成長、最大 handles。報表的表格是把這些摘要再依 process 彙總。
  • CPU 單位 = 每核:100 代表整整用掉 1 個核心,190 代表約 1.9 個核心。跟 VM 有幾個核心無關。
  • 記憶體單位 = MB:Windows 是 Private Bytes,Mac 是 RSS,兩者不能互相比較。
圖 1:每個 CPU 數字都需要「上一次取樣」才算得出來,所以第一個樣本沒有 CPU 值,重開機或 process 重啟後也會重算。

2. 「Resource peaks per process」逐欄解說

avg_cpu_peak — 平均的最高 CPU

  • 意思:每次 run 先取該 process 的最高 CPU,再把所有 run 取平均。
  • 為什麼看:當作「一般情況下 CPU 大概多忙」的粗略基準。
  • 怎麼讀:它是「最高值的平均」,測試種類(壓力測試 vs 閒置測試)占比一變它就跟著變。只適合同一批測試之間比較。

worst_cpu_peak — 最高的 CPU 讀數

  • 意思:所有 run、所有取樣點裡最大的那一個 10 秒平均值。
  • 怎麼讀:它是單一個點,說明「曾經到過這個高度」,不說明「持續」。不會讓 run 失敗。用途是看離門檻還有多遠,例如 254.8 對門檻 280。

worst_sustained_s — 持續高於門檻的最長秒數

  • 意思:某次 run 裡,CPU 連續高於門檻的最長時間(見第 3 節圖 2)。
  • 為什麼看:抓失控的迴圈或卡死空轉。短暫尖峰在重連、載入設定時都是正常的,只有「持續」才是問題。
  • 怎麼讀:0 = 沒有任何一個樣本到門檻;10 = 恰好 1 個樣本到門檻;達 60 秒才失敗。幾乎都是 0,因為所有 process 的峰值都遠低於 280(歷史最高 261.2)。

cpu_gate — 門檻

  • 意思:判定「持續」所用的 CPU 值(每核),所有測試統一是 280(2.8 個核心),要連續 60 秒才失敗。圖上的黃色虛線就是這個門檻。
  • 注意:峰值高過黃色虛線不等於失敗,要連續 60 秒高於才失敗;demAgentSvc.exe 是 observe-only,有量測但不會失敗。較早的 run 當時各測試用過 140 或 240,報表統一用 280 重新計算 worst_sustained_s:最高讀數沒到 280 的 run,高於門檻的時間就是 0。

avg_mem_growth / worst_mem_growth — 記憶體成長

  • 意思:成長 = 「近期平均」減「基準」(見第 3 節圖 3)。負數 = 縮小。
  • 為什麼看:記憶體洩漏的訊號。worst 超過 100 MB 判失敗。
  • 怎麼讀:avg 會正負相抵,洩漏被平均掉,參考價值低;worst 才是有用的那個。成長跟 run 的長度有關,跑得越久越容易看到成長。

worst_handles — 最大 handle 數

  • 意思:任一取樣點的 handle 數最大值。
  • 為什麼看:handle 洩漏最終會讓 process 耗盡資源。
  • 怎麼讀:到 1500 而且最後一個樣本仍在 1500 以上才失敗(圖 4)。目前 stAgentSvc.exe 是 1400,離線 100,值得留意。

3. 三張圖解

圖 2:怎麼知道「持續」?每根柱是一個 10 秒窗口,黃色虛線是門檻 280。左圖是真實 run:最高的一根只有 143.28,沒有任何一根碰到門檻,所以 worst_sustained_s = 0。如果剛好有 1 根高於門檻,值會是 10 秒:秒數 = (最後一根時間 − 第一根時間)+10,1 根就是 0+10;連續 6 根 = 50+10 = 60 秒,達到失敗線(右圖,示意)。注意它量的是 10 秒平均,短於 10 秒的尖峰會被攤平。
圖 3:記憶體成長怎麼算(真實 run)。基準 = 前 3 個存活樣本的中位數,近期 = 最後三分之一的平均,成長 = 近期 − 基準。每次開機算一段(重開機後記憶體歸零,跨開機比較沒有意義),取成長最大的那一段。
剛安裝完的 client 呢?程式沒有暖機豁免:基準永遠取該次測試最前面 3 個存活樣本。一般測試開始時 client 已經在跑,基準是穩定值(例如 STRESS-01、STRESS-08、STEER-06 的基準是 25–29 MB,成長只有 5–8 MB);暖機增幅遠小於 100 MB 的門檻,不會誤判。 若要「等 process 準備好再取基準」,需要先有 thread 數資料,這個工作已列入待辦。
圖 4:handles 規則。啟動瞬間衝高、之後回落不算洩漏(STEER-07 真實情況:3304 → 790 → 約 920);只有一路漲過天花板、結束時還在上面才失敗。

4. 「Resource peaks per process across versions」(CPU 跨版本圖)

已移除「各版本平均峰值(avg)」的趨勢線,因為它會隨測試組成而變,不能當成回歸訊號。目前保留的是「各版本 worst」圖,下面說明怎麼讀它,以及 avg 為什麼被拿掉。

現在畫的是什麼

  • X 軸是 client 主版本(R140 起,每個新版本多一個點),每個 process 一條線;分成 heavy(峰值 ≥ 30%)與 light(< 30%)兩組,避免輕的 process 被壓成一條直線。Mac 另有自己的圖,從 R143 起。
  • 每個點是該版本單一最高的 CPU 讀數(worst)。它是單一個 10 秒平均,不是持續的證據,也不會讓 run 失敗。請當成「曾經到過這個高度」,不要當成趨勢。

為什麼 avg(各版本平均)被移除

  • 測試組成每版都不同:R140 跑 15 種、R142 跑 36 種、R143 跑 57 種、R144 只跑 21 種。壓力測試占比一高,平均自然升高。
  • 每個點是 10 秒平均的最高值,跑得越久、重複越多次,越容易遇到一個高點。
  • 單次 run 本來就很不穩定:同一個測試、同一個版本,STRESS-26 的峰值在 16 次 run 之間是 49 到 162。
圖 5(真實資料):左邊是舊趨勢圖的算法,右邊只比較兩個版本都跑過的測試。143→144 左邊只升 3.7,右邊同樣 14 種測試升了 17:平均會誇大,也會掩蓋。
注意:R142 同一批測試確實上升(24 種裡 17 種升超過 20%),R143 又降回來。資料看不出原因(可能是產品、VM 或取樣條件),這該另外查證,而不是靠趨勢圖開 ticket。

5. 「Memory per process across versions」(記憶體跨版本圖與表格)

欄位意思怎麼讀
Avg baseline MB各次測試開始時的記憶體,取平均受前一個測試留下的狀態影響(例如 STRESS-03 的基準是 144 或 192 MB,一般測試約 25–29 MB)
Avg peak MB各次測試最高記憶體,取平均跟測試時間長短有關
Worst peak MB單次測試的最高記憶體單一點;超過 500 MB 會判失敗
Samples參與平均的「測試 × run」列數太少(例如 < 5)不要下結論
Tests該版本跑過幾種不同的測試先看這欄:兩版的數字差很多,就不能直接比
Runs該版本的 run 數重複次數
  • Windows 是 Private Bytes,Mac 是 RSS,兩者不可互比,所以分開兩張圖。
  • 各版本的「平均記憶體成長(Avg growth)」欄已移除:成長有正有負,平均會相抵,看不出洩漏。要看洩漏請看「Resource peaks per process」表的 worst_mem_growth。
  • 「Large steps」註記:相鄰版本的平均基準上升 50% 以上且超過 10 MB 時,報表會自動寫一行,並用「兩版都跑過的測試」重算一次,避免把測試組成的改變當成產品變化。
圖 6(真實資料):每版平均基準與測試數。R142 起翻倍,報表註記是 NPA 功能開啟;但同一版的測試組成也改變了,兩個原因分不開。

6. 數字上升,要開 ticket 嗎?

先問三個問題,三個都「是」才值得開:
1. 測試組成一樣嗎?看 Tests 欄,或改看「同一個測試跨版本」。
2. 同一個測試本身也升了嗎?並且不是只有一次 run。
3. 有 gate 命中嗎?sustained、memory growth、handles 任一個。
情況要開 ticket?原因
Gate 命中(sustained ≥ 60 秒、growth > 100 MB、handles 不降回)要測試已經失敗,這是產品訊號
同一個測試連續兩個版本都明顯上升先查再決定需排除 VM 與取樣條件
記憶體 Avg baseline 上升,但 Tests 數量不同不用測試組成改變,不是同一批比較
worst 圖出現一個高點(worst_cpu_peak)不用單一 10 秒平均,不代表持續
worst_sustained_s = 10 或 20不用1 到 2 個窗口,距 60 秒的失敗線很遠
worst_handles 接近 1500(例如 1400)盯著還沒失敗,留意趨勢

7. 名詞

名詞意思
取樣 / 窗口每 10 秒讀一次;每個 CPU 值是「與上一次相比」的 10 秒平均
每核 CPU100 = 1 個核心,與 VM 核心數無關
gate(閘門)測試結束後檢查資源數字,超過門檻就判這個 run 失敗
sustained連續高於門檻的時間,預設 60 秒才失敗
baseline / recent記憶體成長的起點(前 3 個存活樣本中位數)/ 終點(最後三分之一平均)
observe-only只記錄、不判失敗的 process(demAgentSvc.exe 和 epais.exe;有 Shuttle/Keystone 監控改動時還有 shuttle-ctl.exe、sovin.exe,以及 Mac 的 keystone-auth、shuttle-launcher)
Private Bytes / RSSWindows / Mac 的記憶體度量,不可互比
